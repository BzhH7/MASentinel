## 方案设计
MASentinel 是一款面向多智能体系统的自动化测试框架，采用分阶段流水线架构：静态分析阶段通过 profile_builder 提取被测系统的 agent、tool、消息边等语义画像；测试生成阶段利用 testcase_generator 与 validators 生成并校验确定性测试用例（包括契约、故障模式、跨 agent 交互等）；执行阶段由 case_runner 以无人值守子进程方式运行被测系统并采集完整 trace；评估阶段通过 rule_oracle 对终止/崩溃/agent/tool/消息边/输出契约进行裁判，随后由 coverage 计算 MASCov 多智能体语义覆盖率；诊断阶段由 fault_classifier 区分应用层与 AutoGen 框架层故障并排除非目标问题，最后由 project_report 汇总生成赛题要求的项目报告。整个过程对被测系统零侵入，仅依赖输入输出与 trace。

核心流程：
- `RequirementAnalystAgent` 抽取可验证需求。
- `SystemModelingAgent` 复核 agent、tool 与 message edge 语义图。
- `TestDesignerAgent` 分批生成补充测试，确定性生成器补齐覆盖类型。
- `InteractionAdapterAgent` 为交互式目标系统规划无人值守输入适配。
- `ExecutionMonitorAgent`、`FaultDiagnoserAgent`、`FalsePositiveAuditorAgent` 完成异常归纳、故障定位与误报审计。
- `ProjectReportAgent` 汇总三套系统的最终提交报告。

## 测试覆盖率指标设计
MASCov 多智能体语义覆盖率由 13 个指标加权构成：agent_coverage（agent 覆盖率）1.0, tool_coverage（工具覆盖率）1.0, message_edge_coverage（消息边覆盖率）0.75, requirement_coverage（需求覆盖率）0.1667, req_intent_coverage（需求意图覆盖率）0.1667, req_verified_coverage（需求验证覆盖率）0.1667, state_coverage（状态覆盖率）0.5833, fault_mode_coverage（故障模式覆盖率）0.5714, contract_coverage（契约覆盖率）0.8182, effective_workflow_rate（有效工作流率）1.0, trace_completeness（trace 完整度）1.0, root_cause_evidence_rate（根因证据率）0.5，最终加权得到 mascov=0.6914（以 system1 为例）。不同系统各指标权重一致，但具体数值依执行结果变化。该设计既关注覆盖充分性，也强调可解释性与故障定位能力。

| 指标 | 含义 |
|------|------|
| AgentCov | 测试 trace 覆盖到的目标 agent 比例 |
| ToolCov | 触发或观测到的工具调用覆盖比例 |
| EdgeCov | agent 间消息边覆盖比例 |
| ReqCov | 需求点被测试用例绑定并执行的比例 |
| ReqVerifiedCov | 需求至少被一个无目标故障、无非目标阻塞的用例有效验证的比例 |
| ContractCov | 通用契约测试模式（artifact/filesystem/tool/handoff/CLI 等）的覆盖比例 |
| EffectiveWorkflowRate | 非阻塞用例中真正进入 agent/tool/message 工作流的比例 |
| TraceCompleteness | 当前 trace 是否包含支撑 missing 类故障判断的关键观测类型 |
| RootCauseEvidenceRate | 确认故障中具备代码证据或强 trace 证据的比例 |
| StateCov | 正常、异常、超时、终止等执行状态覆盖 |
| FaultCov | 已覆盖的故障模式类型比例 |
| MASCov | 上述指标的综合语义覆盖分数 |

## 效果分析
MASentinel 在三个系统上的综合效果显著：**system1** 发现 5 个根因故障，MASCov 0.6914；**system2** 发现 4 个根因，MASCov 0.8571；**system3** 发现 2 个根因，MASCov 0.5952。每套系统均完整覆盖 agent/tool 交互、消息传递、终止条件、文件安全、恢复状态等关键维度，且所有确认故障均可通过修改被测系统代码或 AutoGen 配置（如 human_input_mode、终止条件、路径约束、分页逻辑）解决，完全符合赛题对“目标软件故障”的定义。通过 FalsePositiveAuditorAgent 的后验审计和 fault_classifier 的逐层过滤，三个系统的疑似误报率在 20%50% 之间（system1 3/10、system2 1/6、system3 3/5），说明当前诊断流水线已具备基本的噪声抑制能力。但部分故障证据强度偏弱（如仅 trace_only），未来需加强故障复现与确定性代码定位，同时对 TURN_BUDGET_EXCEEDED、MISSING_AGENT 等非目标问题的拦截策略可进一步细化以降低对 oracle 干扰。整体上，MASentinel 展示了一套可复现、可审计、可扩展的多智能体系统自动化测试与故障定位方法论。

## 下一步改进计划
- 增强故障证据采集：对每组疑似故障增加复现重试（3次），收集可对比的 trace/diff 以提升 root_cause_confidence 至 code_evidence 级别。
- 精细化测试策略：针对 coverage 中低分区（如故障模式覆盖率、状态覆盖率、agent/tool 未激活项）扩展测试用例模板，引入定向变异与多轮交互扰动生成。
- 闭环自愈学习：对于已修复故障，将修复验证 case 加入回归集；对反复出现的模式（如终止条件缺失）提炼为通用检测规则。
- 提升 oracle 鲁棒性：将 TURN_BUDGET_EXCEEDED 与 MISSING_AGENT 等非目标问题与真实故障的判别自动化，减少对 oracle 失败率的人工干扰。
- 系统适应性扩展：针对更多 AgentOS 框架（如 CrewAI、LangGraph）构建适配层，验证 MASentinel 的泛化能力。
